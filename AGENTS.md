- Global integration credentials (Evolution, Google OAuth, Stripe) live encrypted (AES-256-GCM, server-derived key) in deny-all `platform_integration_secret`; read them only via `resolveIntegration` in `src/lib/integration-secrets.server.ts` (env is fallback) — why: owners configure in Master without Secrets and values never reach the browser.
- Installation ownership is auto-claimed inside `bootstrap_remix_instance` by the first confirmed Auth account, once, under an advisory lock — why: no manual activation code, still race-safe.
- Two independent auth sessions per browser: subscriber (generated client, default storage key) for `/entrar` and `/app/*`; owner via `superadminSupabase` (`src/lib/auth/superadmin-client.ts`, own storageKey) for `/superadmin` and `/master/*`. Shared code imports `supabase` from `src/lib/auth/realm-supabase.ts`, which resolves the tab's realm (admin paths, or `/app` during a Master impersonation in that tab); server-fn bearer comes from `attachRealmSupabaseAuth` in `src/start.ts`; sign-outs use `signOutRealm` (scope local) — why: owner and subscriber stay logged in side by side without overwriting each other. Enforced by `scripts/verify-auth-realms.mjs`.
- Subscriber finance screens (month overview, statement, planner/calendar, MárcIA chat) are shared presentational components in `src/components/finance/*` fed by `/app` (real server functions) and `/demo` (fictitious data in `src/lib/finance-demo-data.ts`, scripted chat with the same `MarciaChatController` contract); period/status rules live in `src/lib/finance-period.ts` — why: the demo always mirrors the real product without duplicate UI.
- Removed areas stay as redirect-only route files to their new equivalent (e.g. `/app/calendario` → `/app/planejamento`) — why: old links, reminders and bookmarks keep working.
- The central WhatsApp channel is exclusive: `platform_support_channel.active_provider` changes only through the `switch_central_channel` RPC (trigger-guarded; it only activates when the shared channel row describes that provider as connected, Meta also needs `test_ok`), and sends require `isActiveChannelConnected`; webhooks drop inbound messages from the inactive provider — why: QR Code and Meta can never answer at the same time.
- Post-purchase WhatsApp onboarding lives in `src/lib/purchase-onboarding.server.ts` (pure rules in `purchase-onboarding-rules.ts`): idempotent per billing event, runs after subscription/credits, never throws into payment webhooks, stores only hashes of one-time activation codes/tokens, and binds a phone to a tenant only on the first valid reply from the exact buyer phone (codes/tokens from other numbers are rejected without being consumed) — why: no silent phone binding and no duplicate sends. Enforced by `tests/purchase-onboarding.test.ts` and `scripts/verify-central-channel-onboarding.mjs`.
- AI provider selection (Lovable AI default, optional single BYOK OpenAI/Anthropic) is read from `ai_provider_config` inside `lovableAiChat`; BYOK keys are stored via `integration-secrets.server.ts` and only shown masked — why: one entry point for every AI call and keys never reach the browser.
- New subscriptions always start from an explicit active plan: generic signup CTAs go to `/#planos`, `/entrar?modo=signup` without a valid active `plano` redirects there, and both `createCheckoutCompany` (`src/lib/plan-selection.ts`) and the `create_checkout_company_atomic` RPC reject a missing/inactive slug — why: no company or subscription is ever created on an assumed default plan.
- Human form values go through shared helpers: money via `src/lib/money.ts` + `MoneyInput` (UI shows "R$ 0,00", storage/Stripe keep integer cents), phones via `src/lib/phone.ts` (BR mask, E.164 on the server), e-mails via `normalizeEmail`/`emailError` in `src/lib/masks.ts`; technical IDs/tokens are never masked — why: one conversion path prevents 100x price errors and inconsistent contact data.
